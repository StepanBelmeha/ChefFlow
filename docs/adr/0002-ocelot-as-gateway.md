# ADR-0002. Спосіб маршрутизації зовнішніх запитів
# Статус

Accepted (2026-06-19)

# Контекст

Після поділу моноліту на чотири сервіси (AuthService, RecipeService, TaskService, SocialService) клієнтська частина ChefFlow, реалізована на чистому JavaScript через Fetch API, звертається до бекенду з браузера. Без єдиної точки входу клієнт мав би знати адреси всіх чотирьох сервісів та змінювати їх при кожному перерозгортанні. Крім того, перевірка JWT-токена зараз виконується в кожному контролері окремо — у мікросервісній архітектурі це дублювання логіки між усіма сервісами.

# Розглянуті варіанти

Варіант 1: Без шлюзу
Клієнт напряму звертається до кожного сервісу за окремою адресою. При зміні порту або адреси будь-якого сервісу необхідно оновлювати JS-код на клієнті. Кожен сервіс самостійно валідує JWT-токен.

Варіант 2: YARP (Yet Another Reverse Proxy)
Вбудований у ASP.NET Core проксі, що налаштовується кодом на C#. Дуже гнучкий та продуктивний, але конфігурація прописана в коді — зміна маршрутів потребує перезбирання.

Варіант 3: Ocelot
API-шлюз для .NET, що налаштовується декларативно через JSON-файл. Підтримує маршрутизацію, перевірку JWT, обмеження запитів. Маршрути змінюються без перезбирання проєкту.

Варіант 4: Хмарний шлюз (Azure API Management)
Потужне рішення з моніторингом та аналітикою, але потребує хмарного середовища та є надлишковим для навчального проєкту.

# Рішення

Обрано Ocelot. Клієнтська частина ChefFlow звертається до єдиної адреси шлюзу, Ocelot перенаправляє запити до відповідного сервісу на основі префіксу маршруту. Перевірка JWT виконується на рівні шлюзу один раз, а не в кожному сервісі окремо. Конфігурація маршрутів описується в ocelot.json, що дозволяє змінювати маршрутизацію без зміни коду.

Приклад маршрутизації:

/api/auth/** → AuthService
/api/recipe/** → RecipeService
/api/usertasks/** → TaskService
/api/favorite/** → SocialService
/api/note/** → SocialService
Наслідки

Позитивні:

клієнт має єдину адресу і не залежить від внутрішньої структури сервісів
JWT валідується в одному місці — логіку не треба дублювати в кожному сервісі
зміна адреси будь-якого сервісу потребує лише редагування ocelot.json

Негативні:

з'являється додатковий процес шлюзу, який треба запускати разом з чотирма сервісами
шлюз стає єдиною точкою відмови — якщо він недоступний, клієнт не може звернутись до жодного сервісу
кожен запит проходить додатковий мережевий крок через шлюз
